## 2. R1（残留 #21）：blocked 的原因上摘要面

**缺陷**：`core/runtime.py` 的 blocked 路以 `failure=None`、note 硬编码 "blocked by model" 收尾，
`termination_reason` 无人写 ⇒ 结果对象、`episodes.csv`、`episode_summary.json` 三处读出来都是
"失败，未说明原因"，原因只在事件流里。

**修法**（D3''：`FailureCode` 枚举不扩，§2.2 的停工条款未被触发）：原因取决策对象自带的
`rationale`（空则回落常量 `BLOCKED_FALLBACK_REASON`，**命名模型的沉默，不替它编原因**），
落到 `terminated_blocked.reason`、`_finalize` 的 note 与新字段 `Runtime.blocked_reason`。

**为什么是 `blocked_reason` 而不是 `termination_reason`**：这是改动撞上的一处真实反作用，
当场记、当场定。照字面直接写 `termination_reason` 会把 ALFRED 文本后端的封口词表覆盖掉
（`test_control_outcomes_seal_the_episode_at_once[blocked-AGENT_BLOCKED]` 由绿转红）——
那个后端在 `_finalize` 里 `if self.termination_reason is None: …`，把 `failure is None`
封成 `AGENT_BLOCKED`。换字段之后两边各得其位：物理后端报决策自己的话，封口后端保住 `AGENT_BLOCKED`
而散文仍在 `artifacts.note` 与事件流里。两侧各有一条测试钉住，互为反面证据。
**若当时只跑新测试，这条反作用会带进正式批。**

### 两条最干净的逐集证据链

1. **vlm / c3 / item0 黄色方块**（声明 `obj_yellow_1`，cube）：**7/7 轮与 4/4 轮帧端都看见了黄色**，
   但两次 repeat 都报 `['yellow', 'cuboid']` ⇒ `bound 0/7`、`actionable 0/7`。
   **一个词的形状分歧把一件物体从回路的世界里删掉了**，直到预算耗尽。同一格另外五项都能行动。
2. **stub / c1 / item3 紫色圆柱**：前 3 轮检测 `['purple', 'cuboid']`（声明 cylinder）⇒ 形状失配；
   后 3 轮紫色整段从分割里消失 ⇒ 未检出。`bound 0/6`。

### 缺陷落到一行代码

同一个问题——"这条声明指向哪件物体"——盘上有**两套规则**：`GroundingMap._lookup` 写明
"唯一颜色优先，形状误读不得覆盖桥"，而回路的目标侧 `bind_attributes` 要求帧端**实测**的每个属性
与声明逐项相等、且恰好一个实体命中。**更严的那套恰好用在了决定结果的地方。**

### 差分设计的两道门（SPEC §6）

- **"stub 同样死"这一关**：过了，且死法相同（stub 两格的主导环也是 b，成因同样是形状失配）。
  ⇒ **"瓶颈是 VLM"在 v0.5 的证据下不成立**：把 VLM 换成确定性分割器，同一个环照死不误。
- **privileged 对照**：4/4、四环全 0 ⇒ 排除决策器。

### 这条判定**不**说什么

只覆盖 E2' 这 12 集、两个 case、两次 repeat；`bind_attributes` 的"恰好一个命中"分支（歧义）
本批一次都没走到（c3 两黄在 v0.4 R3 的复合键下分得开），**这条分支的死法无读数**，不得当作"没问题"；
间歇漏检 38 个项-轮是真实贡献，但按预登记门槛不归属给 a 环。

## 4. RQ12（A2 触发机制）：假设 + 判据 + 最小验证设计，不是率

语料 **187 个模型席集**（v0.3 E1 的 12 个 `planner=deepseek` 格 153 + v0.4 E1' 3 个 run 34），
**3 个触发集**（v0.3 两集 + v0.4 一集）。仪器在 v0.4 E1' 的 34 集上与 shipped 记分器
`lh_score/long_horizon_v0.json` 的 `detail.dependency_edges` **逐项相等（34/34）**。

三个触发集的形状完全同构：`v1`（`trigger=initial`）无边 → 某版重规划视图首次写下
`kind=recovery` 的边（`violated="False"`）→ 后续某版视图 `trigger=dependency_violation`，
同一条边转为违反。模型自己写的理由是同一句话的三个实例：

> `obj_green_5 was displaced out of tray_left to let obj_blue_1 in and must be restored before the task ends`

| 假设 | 协变量 | 可测判据 | 最小验证设计 |
| --- | --- | --- | --- |
| **H1**（内容，后验生成） | 模型**观测到"自己已放好的东西被另一个放置挤出去"** | 在有位移扰动的格里，"出现过该观测"的子集边触发率显著高于未出现的子集；触发集的边 `note` 含位移语义 | 干预式两格 ×12 集（c2 位移可观测 / c3 语义不同），只在该观测确实发生的集上读条件触发率；上界 ≈930 请求；0 触发 ⇒ rule-of-three 上界 3/24 = 12.5% |
| **H2**（事前 V4） | 边只出现在**重规划**视图，从不在初始视图 | 187 集的每一个 `trigger=initial` 视图 `dependencies` 恒为空 | **零成本**：现有语料 187 个初始视图 0 反例；写成契约测试是 v0.6 的输入 |
| **H3**（事前 V7） | 写边与"进入持续恢复区"共变，但**方向未定** | 在恢复计数被干预的条件下，边触发率随计数单调上升 | 同 H1 的批，按 `recovery_action` 计数分档（0 / 1–3 / ≥4）读条件率与 Wilson 区间 |
| **H4** | 触发集的边全是 `kind=recovery` 且最终全部被违反 | 同上；**n=3 不能排除"别的 kind 只是没出现"** | 现有语料读数，不得写成"模型只会写 recovery 边" |

**关键的方向警告**：触发**之前**的 `recovery_action` 计数在三个触发集上都是 **0**；
全集计数（13/11/6）高于其余 184 集的最大值（5），**但很可能是写边之后的义务驱动了后续恢复**。
⇒ 相关成立，因果方向未定，H3 按"方向未定"交付。

**具名负读数**：**触发机制在席位 / run / case 三个维度上不可归因**——
agnes 3/172 vs sensenova 0/12，case c2 2/13。要归因必须换设计，不是加集数：
按 1/34 的实测率，"两位数触发"需要 ~680 集、约 26,000 请求。
